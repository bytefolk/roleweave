# 从需求到产品验证方案

任务数据见 [product-validation.json](product-validation.json)。这是虚构客户的只读方案交付案例，目标是验证岗位分工和交接，不声称已经开发原型或获得客户反馈。

## 需求与组队

将 `brief` 发给 CEO。CEO 应先给出目标、约束、待澄清问题、拟参与岗位及各自交付物。遇到关键未知项时，用户先补充或明确允许按假设推进。

用户审阅建议，通过现有群组入口选择岗位。入门公司使用 CEO → CTO → COO；产品公司使用 CEO → CPO → CTO → COO。用户在本次请求中明确顺序和职责，选择接力模式。把 `brief` 和 `relayInput` 一起作为群组输入；不要假定共享 context 目录已被自动接入。

| 阶段 | 岗位 | 预期交付 | 下一阶段需要什么 |
| --- | --- | --- | --- |
| 目标澄清 | CEO | 已知事实、假设、约束、成功标准 | 用户问题和明确的验证目标 |
| 产品定义（完整公司） | CPO | 最小范围、排除项、验证假设 | 可实现的产品范围和验收方法 |
| 技术规划 | CTO | 技术方案、风险、研发岗位建议 | 实施依赖、需要的权限和技术验证项 |
| 交付整合 | COO | 执行顺序、交接清单、用户验收项 | 用户可检查的完整方案 |

每个接力步骤收到原始任务和前驱可信结果的有界摘录。摘录不是完整跨岗位记忆；需要保留的关键约束应写入本次任务，必要时由用户补充材料。

## 并行评估

入门公司可选择 CTO、COO 并行评估；完整公司可选择 CFO、CMO、CISO 分别分析成本假设、市场假设和安全风险。使用 `brief` 加 `parallelInput`。并行执行产生独立结果，不自动读取其他成员尚未完成的输出，也不会自动汇总。

用户将需要的可信结论交给 CEO 或 COO 整合。新增执行岗位时，使用现有招聘配置确认职责、Agent、预算和权限，随后显式加入群组；不能把聊天中的“建议招聘”当作已经完成招聘。

## 验收与失败处理

- 按任务数据的 `acceptance` 逐项人工验收；缺少证据的效果或客户反馈仍记作待验证。
- Agent 不可用：配置连接后再启动；保存组织并不保证岗位已经可运行。
- 预算不足或执行冲突：查看岗位状态与记录，结束冲突任务或调整明确授权的预算后重试。
- 前驱失败、取消或没有可信终态：后继不会被调用，查看接力阻塞记录；不能假装完整交付成功。
- 重启后可回读已记录结果，但不会自动重放未完成的模型调用。用户检查记录后决定继续方式。
- 用户验收后保留群组记录。当前群组没有“任务团队完成后自动归档”的专用生命周期，不把移除成员等同于裁撤岗位。

实际软件开发、文件交付或外部反馈采集需要另配执行能力与权限，超出这个只读场景的验证范围。
