# 四类执行团队与跨团队交付

使用 [AI 产品交付公司](../scenarios/ai-product-delivery/README.md) 副本。该场景包含五个经营职能和十四个专业岗位，共十九个岗位。团队名单见 [teams.json](../teams.json)，阶段定义见 [team-playbooks.json](team-playbooks.json)。这些文件是案例操作资料，不是平台新接口或自动编排配置。

## 团队结构

```text
CEO
├── CPO
│   └── 产品经理（团队负责人）
│       ├── 用户研究员
│       └── 交互设计师
├── CTO
│   └── 研发负责人
│       ├── 软件架构师
│       ├── 前端开发工程师
│       ├── 后端开发工程师
│       └── 测试工程师
├── CMO
│   └── 营销策划负责人
│       ├── 内容策划
│       └── 增长分析师
└── COO
    └── 交付负责人
        ├── 项目协调员
        └── 客户支持分析员
```

CXO 确定目标和资源取舍，团队负责人协调与整合，专业岗位交付具体产物。测试工程师独立于前后端实现者；用户仍是最终验收者。这个汇报结构不决定任务执行顺序，也不授予额外权限。

## 共同任务与准备

合成任务见 [product-delivery.json](product-delivery.json)：为虚构内容团队形成 AI 选题助手的 MVP 交付包，包含产品规格、交互与接口、前后端代码草稿、审阅记录、营销方案、交付说明和验收表。

先复制整个工作区，在 RoleWeave 中打开副本，再连接参与岗位的 Agent。岗位默认只读：可以在会话中提交代码草稿和文档，但不会写仓库、执行代码、接入真实模型、部署或发布。真实软件测试和真实业务效果仍须另行获得执行条件并验证。

将 `brief` 发给 CEO 或相应 CXO，澄清目标、约束与未知项。用户确认范围后，按团队 `members` 创建四个现有群组。群组成员不自动包含 sponsor；需要 CXO 参与具体工作时，用户另外选择它，不因为头衔自动广播。

## 四个可以分别使用的团队案例

| 团队 / runbook | 阶段和成员顺序 | 交付与验收 |
| --- | --- | --- |
| 产品 / product-discovery | 研究员与设计师并行 → 产品经理与设计师接力 | 事实与假设、范围、交互和可检查的产品规格 |
| 研发 / engineering-validation | 负责人→架构师 → 前后端并行 → 负责人→测试工程师 | 接口契约、代码草稿、独立验证结论、修复记录 |
| 市场 / market-validation | 内容与增长分析并行 → 增长分析师→营销负责人 | 仅依据确认过的能力编写内容，实验方法与未验证结果分开 |
| 交付运营 / delivery-acceptance | 协调员与支持分析员并行 → 协调员→交付负责人 | 可追溯的交付包、阻塞、用户说明和最终验收清单 |

每个阶段都有 `instruction`、`outputs` 和 `acceptance`。小任务可只选需要的团队或阶段；不用每次召集所有 CXO 或全部十九个岗位。

## 用现有群组推进一个阶段

1. 用户选择该阶段的 `mentions`，确认 `mode` 为并行或接力。
2. 本次 `input` 包含合成需求、阶段请求、用户选择的前序产物和关键限制。输出编号是案例交付标签，不是现有 Artifact API 的自动引用。
3. 等待明确的可信终态，审阅产出。对照该阶段验收项记录结果；不要把回合 `completed` 当作业务验收通过。
4. 用 [交接记录](../templates/handoff.md) 选择可继续加工的结论、依据、缺口和下一步。将关键材料显式放进下个阶段输入。

接力会自动提供前驱可信结果的有界摘录；它不保证传递完整文档，原始请求应保留不可遗漏的约束。并行成员不自动获得同批次其他成员输出；跨群组也没有隐式共享，所以跨团队材料仍由用户选择传递。

HTTP 请求仍是原有字段，下面是研发实现阶段的示意：

```json
{
  "input": "合成需求 + 已确认接口契约 + 前后端各自交付要求 + 明确限制",
  "engine": "qoder",
  "mentions": ["frontend-developer", "backend-developer"],
  "mode": "parallel"
}
```

向 `POST /groups/<conversationRef>/turns` 提交；工作区、认证和群组须按现有 API 配置。不要把 `teams.json` 或整个 runbook 直接当请求体提交。

## 独立验证、修复与升级

研发负责人先整合前后端产物，测试工程师再按 [验证记录](../templates/review.md) 提交结论：

- PASS：本次明确范围内的要求有通过证据。
- FAIL：已识别不满足的要求，附预期、实际、证据和涉及的实现岗位。
- NOT_VERIFIED：缺少运行条件或证据；不是通过，也不是已经证明失败。

示例：契约要求空输入返回明确错误，但后端代码草稿没有该分支。测试工程师指出草稿位置、预期返回和复验方法；用户只把这条问题交给后端岗位修正，再将修正结果交给测试工程师。若前后端都受影响，再明确选择双方。runbook 的 `repair.mentions` 是可修复岗位名单，操作时可以选更小的受影响集合。

修复与复验都由用户显式发起；平台不会因为答案包含 FAIL 自动启动下一轮。当前例子的上限是三次完整的验证尝试（含首次验证），最多两次中间修复。达到上限仍 FAIL 时，使用 [升级记录](../templates/escalation.md)，由用户决定补充资料、拆分任务、调整方案、改派或暂停。NOT_VERIFIED 则先补齐资料或运行条件，不假装修复已经让实际测试通过。

## 跨团队顺序

产品规格确认后，研发与市场可基于同一份确认过的产品范围分别推进；它们的专业岗位不重叠。交付运营依赖两边的产物和验证记录。用户最后验收 MVP 包，记录未验证的软件运行、部署和真实反馈，再填写 [复盘](../templates/retrospective.md)。

如果某个回合失败、取消或没有可信终态，先检查现有时间线，不把不可信结果交给下一个团队。重启后回读已记录产出，不自动重放模型调用。相同岗位同时参与其他群组时仍受现有单活动执行和岗位预算限制。
