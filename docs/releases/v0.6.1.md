# RoleWeave 0.6.1

RoleWeave 0.6.1 fixes conversation controls, makes Codex image-attachment delivery atomic, and adds explicit native terminal execution for authorized Codex employees. It covers the three merged fixes after v0.6.0 through main revision `7b4bd937e680de57ea6ba2365ec08879696b3ca8`; the preparation commit synchronizes release versions and documentation. [Release record #631](https://github.com/bytefolk/roleweave/issues/631) tracks review, exact-source checks, publication and independent installer verification.

## Changes

- Conversation controls: stabilize input-tool tips in reduced-motion mode, keep attachment removal at the card's top-right without covering Send, and show each personal-conversation request timestamp once (#625, #626).
- Codex attachments: reject incomplete or oversized sends, keep images visible while messages are accepted and streamed, and pass validated images to Codex's native image input. Upload failures do not silently send text without the intended image (#627, #628).
- Codex execution: let an operator separately enable native terminal execution and tool networking for an employee. Each turn re-reads the employee and organization policy. A full, approval-free grant to an existing project subdirectory permits commands, file changes and Git metadata writes there; other workspace directories stay read-only. Invalid or revoked grants fail closed. Command activity and sandbox failures are visible, and turn cancellation reaps owned processes (#629, #630).

## Compatibility and upgrade

This remains a pre-1.0 preview. Back up the workspace before upgrading. There is no intentional data migration in 0.6.1; existing workspace identities, history and settings are retained. If reverting from 0.6.1 to a version older than 0.6.0, use a copy of a pre-upgrade backup or a separate workspace: older strict readers can reject the optional task, collaboration and relay fields introduced in 0.6.0.

Native execution is **off by default**. An operator must use the employee's `approval_required` mode, enable Read, Write, Edit, Delete and Exec, grant all five operations to an existing workspace subdirectory such as `./repos/project/**` with per-action approval off, and select “Allow native terminal execution.” Git commands use the installed Git executable through that terminal; there is no separate Git tool. Codex CLI 0.163.0 or newer within 0.x is required. Native execution can read host files, while writes are confined to the granted directories; the consent control discloses this distinction. GitHub access also requires the separate “Allow Codex tool networking” consent and follows the host network policy rather than a website allowlist. Model/provider connectivity is independent of tool networking.

On Windows, network-enabled native execution uses the restricted-token sandbox. Denied tool networking requires the elevated sandbox backend and fails closed if that backend is unavailable; the tested Windows host could not start its elevated backend. Native Windows acceptance did verify project and Git writes, an outside-write rejection, real Codex execution and a GitHub remote query with tool networking enabled. Local Agent installations, sign-ins and provider entitlements remain operator-managed.

## Downloads and validation

- macOS Apple Silicon: `roleweave-0.6.1-arm64.dmg` and `roleweave-0.6.1-arm64.zip`.
- Windows x64: `roleweave-0.6.1-x64.exe`.
- Intel Mac, Linux and native mobile installers are not included.

The existing distribution channel is unchanged: macOS packages are not Apple Developer ID-signed or notarized, and Windows packages are not Authenticode-signed. The macOS app verifies a separately signed update manifest, downloads updates in the background and replaces the app on normal exit. Windows verifies the installer checksum against the HTTPS feed and requires confirmation; older unsigned Windows builds that disable in-app installation need a manual upgrade. Publication advances both public update feeds.

Native builds, packaged startup/layout, installer metadata and artifact integrity are checked in CI. User-machine installation, uninstallation, cross-version updates and real provider entitlement require separate product validation.

## Publisher handoff

Follow the [ByteFolk release process](https://github.com/bytefolk/.github/blob/main/RELEASING.md): independent approval of the final preparation head, protected squash merge, exact merged-commit checks, unused-version and main-ancestry checks, and release-tag protection readback. An eligible actor creates one annotated v0.6.1 tag at the recorded commit only after those gates pass.

The existing release workflow freezes these notes from the merged commit, builds both native distributions, signs the macOS update manifest, verifies the draft asset inventory and publishes last. Stop on a failed gate. Before publication, correct preparation through a reviewed source change. After publication, retain immutable v0.6.0 for rollback with a pre-upgrade workspace backup or separate workspace; correct defects in a new patch version. Never replace released assets or move/reuse a tag.
