## Navigation and authority

The existing Inbox rail entry contains Approvals and Reports. Both use the active workspace generation. The approval queue remounts on workspace change so searches, selection and reason drafts cannot cross workspaces. The badge and Pending filter count only non-expired requests that the server says this actor can decide. All, Processed and Expired remain inspectable; a successful verdict stays selected until the next request is chosen.

Approval rows are sorted by request time, newest first. Request descriptions lead, with role/capability below and risk/expiry beside them. Risk and role filters are available immediately; category, execution phase, date bounds and expiry remain in More filters. Batch decisions retain the frozen source boundary and server-declared maximum. Read-only capability overreach and denied tools disable approval, while denial remains available. Update permissions in Organization and submit a new request rather than using approval to bypass the role policy.

The inspector keeps the source, permission disclosure, preview, policy progress and chained approval audit. Its scrolling body and anchored decision footer are separate. Reasons are trimmed before the 1,024 UTF-8 byte count and submission. Scope defaults to once; run is offered only by the validated server context. Busy, expired and unavailable requests cannot submit. A failed submission keeps the reason draft. An uncertain retry re-reads authoritative state before reusing the original idempotency key. A failed snapshot read retains the cached records and disables decisions until a complete read succeeds. A saved approval is distinct from the recovery execution result.

## Reports and traceability

Four metrics summarize the saved snapshot, followed by five flat views: costs, execution records, exceptions, audit records and timeline. Date, role, status and search filters apply to the current snapshot. Dates use the renderer's local calendar day. Moving to Costs clears a run-status/date scope because budgets have neither execution timestamps nor run statuses. Refresh preserves the last successful timestamp and snapshot on failure. Initial loading uses a skeleton; a failed initial read is different from a verified empty snapshot.

- **Execution records:** selecting a row updates the adjacent evidence inspector. Filtering derives selection from visible rows, so a source action cannot target a hidden record. Source actions use the exact position, conversation and turn tuple; timeline uses the real run ID, falling back to turn ID only when no run ID was recorded.
- **Costs:** recorded aggregate usage and the latest-task ratio have distinct meanings. The bar measures latest-task tokens against declared per-task tokens, with a 0–120% scale and a marker at 100%. Text preserves the actual ratio above 100%, including values above the scale. Unobserved usage displays an em dash. Daily limits remain declarations, not inferred consumption. Selecting a role retains the existing budget detail drawer and timeline action.
- **Exceptions:** merge escalation records with failed/indeterminate evidence receipts and deduplicate by role and turn. Evidence-only failures are actionable through their real source. The recovery suggestion is explanatory and does not dispatch a tool or rerun automatically. A new recovery result must come from a new receipt; historical failure records remain visible.
- **Audit records:** paginate a labeled client projection of real `org-audit.v1` records, timestamped approval decisions and terminal execution receipts. Organization changes expand into their concrete role changes. Approval actions focus the exact request; execution receipts trace their exact run. This projection does not claim these are new server audit events or extend the audit-chain contract.
- **Timeline:** events are chronological within each run. Existing class/date filters and grouping remain. A scoped run has an adjacent summary with exact source/evidence links. Clear scope returns to the full snapshot.

## Contract limits

`reports.v1` has no task title, artifact list or narrative result summary. The table therefore leads with the real run/turn identifier, and the inspector explicitly states when no artifact or summary was supplied. Duration derives from terminal receipt timestamps, is absent while running, and rejects invalid/negative intervals. Budget percentages use the existing latest-task contract, not cumulative usage divided by a task limit. The approval risk contract currently records medium/high rule risk; the Low filter is available for compatible records but never infers a lower risk from an optional advice overlay.

No design example records ship in production. No service API or persisted schema changes, billing amounts, automatic retries or new permissions are introduced. Optional report advice, batch controls and theme/locale support remain available.

## Visual and regression validation

The implementation uses native controls and scoped inbox CSS. The approval HTML adds flat state tabs, separate request-time/risk/status rows, compact risk chips, soft active navigation, and a tinted decision footer with an audit hint. Existing permission and scope explanations remain visible because they describe the actual authorization contract. The HTML export has fixed content-box widths that overflow its 1440px canvas; the implementation preserves the intended proportions and fits the available viewport instead.

The Browser plugin is unavailable in this workspace, so rendered validation uses the existing Playwright installation from the linked design system. A temporary fixture renders the native approval and report components without external execution. Browser checks cover 1440×900 desktop, 640px narrow and 960px English/dark layouts, decision locking, failed draft preservation, cached read-only state, all five report views, exact source selection and scoped timeline navigation. Screenshots and fixtures remain under `/tmp`. The actual Electron client is also rebuilt and restarted for local inspection.

Fidelity targets: full-width content with 24/28px insets; 22px page titles; four 84px summary panels; independent queue/detail surfaces with a green selected row; 110px request rows; 58px execution rows; 390px execution inspector, 470px exception inspector and 340px run summary; anchored approval controls; 0–120% budget scale. Existing optional controls and honest contract limits account for additional metadata relative to the illustrative canvas.
