# Jev 产品提案：待我处理、协作建议与交付预检

状态：待产品与技术评审。核实日期：2026-09-22。本文提出交付边界，不表示功能已上线、完成产品验收或取得收益。

## 1. 产品决策摘要

面向同时管理多个 AI 员工的项目负责人，把分散的执行记录变成有事实依据、可以采取下一步行动的建议。
先做 P0「待我处理」的完整闭环，再验证 P1「发送前协作建议」和 P2「交付预检」。
Jev 负责有限选项内的判断；程序负责可确定的事实、权限、状态、执行和证据关联。
用户始终能看到原始规则结果；建议不能降低已有风险、隐藏失败或代替负责人验收。

| 阶段 | 用户要完成的事 | 最小交付 | 放量前需要的证据 |
| --- | --- | --- | --- |
| P0 | 找到需要自己处理的异常并进入处理入口 | Goals / Reports 的事实与建议并列，关联证据、入口、处理回执 | 现有规则对照、无风险降级、无自动执行、真实样本试点 |
| P1 | 在发送前选对员工与协作方式 | 候选岗位与单人／并行／接力模板建议；用户可编辑后发送 | 明确任务意图的数据契约、候选权限检查、应用与发送隔离 |
| P2 | 在交付前找到验收遗漏 | 按验收条目显示已覆盖／需补充／无法判断 | 用户选定材料、逐项证据、缺失项人工标注对照 |

## 3. 用户、问题与收益假设

主要用户是项目负责人：目前需要来回查看目标、失败上报、会话、审批和交付物，自己判断下一步。
协作用户是执行员工和复核员：接到明确的待办与证据，完成后留下可追溯结果。
管理员负责开启试点、配置服务凭据和数据范围；开启服务不等于授权上传任意任务内容。

| 场景 | 介入前 | 介入后 | 待验证的收益 |
| --- | --- | --- | --- |
| P0 | 逐条翻记录，失败原因与下一步分离 | 同一事项看到事实、建议、证据和处理入口 | 减少定位与分派耗时，且重要问题漏报不增加 |
| P1 | 凭记忆选人、选择并行或接力，发送后再纠正 | 先预览可编辑方案，再明确发送 | 减少错误派工及返工，且总成本不增加到不可接受 |
| P2 | 执行结束后人工逐项核对 | 先看到待补材料与对应要求，再人工验收 | 更早发现遗漏，且不会把无证据结果标为已验收 |

以上收益均为假设。当前没有本项目试点结果、耗时基线或成本对照，统一记为 `NOT MEASURED`。

## 4. P0：待我处理

入口沿用 Goals 详情和 Reports 失败升级；先共用一套事项呈现与处理回执，不先建设独立工作台。
负责人打开事项后依次看到：规则事实 → Jev 建议及其依据范围 → 可查看的证据 → 已有处理入口。
同一失败在两个入口出现时，用工作区内的执行／目标引用关联，处理结果回到同一事项；保留两处原始记录。

示例为设计示意，并非真实项目记录：

> 发布准备：需要补充验收。
> 事实：构建记录存在，验收清单所要求的 Windows 验收记录缺失。
> 建议：先补充该项验收，再由发布负责人复核。
> 入口：查看验收清单、打开相关会话、准备交接。

“记录是否存在”由程序检查；资料不足时不得推断“已通过”或“只需忽略”。
在当前 no-body 输入边界下，示例中的验收语义判断尚不能实现；首版仅针对已存在的状态和错误码提供有限分类。
已知错误码能直接确定的“预算不足”“等待审批”等优先使用规则，不为确定性分类增加模型调用。
若需要根据目标重要性、影响范围、依赖和重试情况判断优先级，必须先定义并评审这些新增字段。

处理流程：查看事项 → 查看证据 → 打开审批／会话／交接草稿 → 用户执行原有动作 → 读取实际结果 → 显示处理回执。
点击“准备交接”只生成可编辑草稿；发送、重试、审批、状态修改均走已有入口并由用户触发。
打开入口、采用建议、执行成功、事项解决分别记录；不能因按钮被点击就标记解决。
只有已有系统事件或负责人明确确认才能记录解决；失败、部分成功和等待外部验收必须继续可见。

## 5. P1：发送前协作建议

入口位于员工选择与群聊输入区，用户明确请求建议后预览候选方案。
示例任务：“整理本周发布说明，核对兼容性风险，交给我审核。”
建议结构：变更研究员收集证据 → 发布工程师起草 → 复核员核对 → 用户审核；使用已有接力语义。
复杂规划仍由规划 Agent 或负责人完成；Jev 从有限模板中判断，不直接创造执行图或 token 预算。

流程：准备任务摘要 → 检查可用候选 → 获取建议 → 用户查看／编辑 → 应用到选人和模式控件 → 用户点击发送。
程序先排除无权限、已删除或不可用岗位；模型输出必须再次校验属于有效候选集合。
“应用建议”只改变尚未发送的控件；不得创建执行、调整审批策略、停止其他员工或修改已发送消息。
发送前候选或任务摘要发生变化时，使原建议失效，提示重新获取或继续手动发送。
当前选择和建议并列显示；不同则标注“建议未采纳”，不自动替换选人、模式或顺序。

[#430](https://github.com/bytefolk/roleweave/issues/430) 当前允许岗位 `{ id, name, mode }`，[#431](https://github.com/bytefolk/roleweave/issues/431) 允许成员名单和当前模式，均禁止发送任务正文。
这些信息不能区分相同成员面对的“并行调研”和“起草后复核”；缺少任务意图时，产品应弃权，不宣称任务匹配准确。
未来建议增加用户单次确认的摘要输入，见第 7 节；该契约未完成前，P1 保持现有手动选人与发送流程。

## 6. P2：交付预检

入口位于交付物与验收清单附近，由用户选择本次待检材料后触发。
流程：选择验收条目及材料 → 程序检查必需文件／记录 → 对获准材料逐项判断 → 显示证据与遗漏 → 补充或交复核员 → 负责人验收。
每项输出仅为“已覆盖／需补充／无法判断”，并标出对应材料位置和仍缺少的信息。
“已覆盖”表示输入材料中找到对应内容；不表示内容事实正确、测试通过、已经发布或负责人已验收。
规则先检查必需文件、链接可达性和明确的测试结果；语义覆盖、要求与表述是否一致才交给模型。
模型不能凭空生成证据引用；只允许引用本次授权输入中的材料 ID，并由程序验证可访问性。
程序先构造“验收条目 × 候选片段”的判断集合；Jev 返回有限选项，界面文案与交接草稿由本地模板产生，复杂撰写另交获准的 Agent。
引用可访问只说明对象存在且可读，不证明内容支持结论；“材料是否支持该项”须单独判断并保留供复核的原始位置。
缺验收条目、缺相关材料、存在互相矛盾的版本或引用失效时，输出“无法判断”，不能给出整体通过结论。
任务完成度与用户满意度分别记录；可以参考 [TypeSafe 官方运行记录评估示例](https://evals.typesafe.ai/agent_trace_observability)，但不沿用其中的自动处置权限。
当前 no-body 契约不足以支撑语义预检；P2 为后续阶段，不借用现有 metadata 接口上传交付正文。

## 7. 输入输出契约与数据边界

下表是产品所需最小契约，不表示相应字段已在当前 API 存在。已有输入与新增输入必须分版本评审。

| 范围 | 最小字段 | 边界与缺失行为 |
| --- | --- | --- |
| 当前 P0 健康建议 | 绑定执行的 `status`、`errorCode` | 沿用 #423 最初 no-body 边界；信息不足则无建议 |
| 本地事项关联 | 目标／执行引用、事实来源、快照版本、现有权限 | 在本地关联；无需把可识别的内部 ID 或完整路径发送给 Jev |
| 未来 P0 优先级 | 经评审的影响等级、依赖状态、重试次数、待审批状态 | 使用有限结构字段；无来源的等级不得补猜 |
| 未来 P1 opt-in | 用户编辑并确认的 `taskSummary`、候选岗位能力标签、有限流程模板 | 默认不提供；禁止自动读取或复制输入框正文 |
| 未来 P2 opt-in | 验收条目、用户选定的最小材料摘要／片段、材料版本、可引用片段 ID | 默认不提供；有权限访问不等于已获准外发 |
| 建议输出 | 状态、有限选项、适用对象、输入版本、可验证证据引用、生成与过期时间 | 所有模型字段校验后才展示；任意无效引用使相应建议弃权 |
| 诊断输出 | provider/model、问题版本、耗时、成本、退化原因 | 不记录 key、正文、摘要或完整材料；不足以计算成本时记 unknown |

opt-in 必须让用户看到实际将发送的字段、接收服务和范围，再执行本次请求；不因启用 Jev 总开关而默认批准。
摘要变化、材料扩大或工作区切换时重新确认；撤销后禁止新请求，不能承诺撤回服务端已经接收的数据。
新契约明确字段白名单、长度上限、脱敏规则和保留周期；这些值在实现前冻结并加入请求快照测试。
凭据仅由服务端配置使用，不返回渲染端，不进入日志、导出、PR 或示例；不复用其他连接器 token。
目前不能据已有仓库代码确认外部服务的数据保留政策；扩大数据范围前需核对服务说明和部署要求。
切换 endpoint 是接收方变化，应由管理员明确配置；保留超时、限流和每次操作的调用上限。
离线评测数据在获得单独授权后按冻结的保留周期保存，并与运行日志隔离；运行日志只保留去标识化引用、输入摘要的 digest、结果和诊断，不留输入内容。
公开 PR 不附真实任务正文或未经授权的试点数据。

## 8. 程序事实、模型判断与退化

| 事项 | 程序负责 | Jev 可提供的增量 |
| --- | --- | --- |
| 失败与审批 | 原始状态、错误码、待审批实体是否存在 | 获准信息充分时，建议人工关注类别 |
| 岗位删除后无人负责 | 岗位 ID 与目标绑定关联，验证有效负责人 | 首版无需模型；不能用置信度代替关联结果 |
| 目标久未推进 | 最近事件时间与已配置预期周期对比 | 只有业务背景充分时再评估提醒优先级 |
| 记忆来源 | 可用性、权限、条数、配置状态 | 有任务意图及来源描述后再评估相关性 |
| 历史上下文 | 实际携带范围、截断量、启用开关 | 无内容依据时不判断“语义过时” |
| 交付预检 | 文件／测试记录、版本、引用有效性 | 对获准材料判断语义覆盖，允许弃权 |

[官方 primitives](https://docs.typesafe.ai/primitives) 提供 Choice、Score、Noul；本提案将复杂问题拆为有限判断，再由程序组合显示。
原因、下一步和证据均从程序提供的有限代码／引用候选中选择，界面用已审核文案模板呈现；不要求 Jev 生成自由文本、摘要、任意引用或完整计划。
Choice / Score 的置信信息和 Noul 概率不等于本项目实测准确率；阈值必须在独立样本上校准，不能展示成“成功概率”。
数据缺失先由程序判定；不能用高置信回答绕过输入充分性检查。Noul 接近不确定区间时必须弃权。

| 状态 | 用户看到什么 | 业务行为 |
| --- | --- | --- |
| 禁用／缺少 key | 原有页面与规则结果 | 无 Jev 请求，不增加操作前置条件 |
| 信息不足／置信不足 | 不显示可采用建议；显式建议区说明缺少什么 | 保留手动流程，不能输出默认推荐掩盖弃权 |
| 超时／限流／响应无效 | 原有事实保留；显式建议区可显示暂不可用 | 有界等待后退回规则，不阻塞发送、审批与查看 |
| 有效建议 | 规则事实与建议分别标注 | 仅展示或在用户点击后预填 |
| 过期／对象变化 | 旧建议不可应用，可重新获取 | 禁止旧结果覆盖新任务或其他工作区 |
| 与事实冲突 | 原事实保留，建议标为未采纳或丢弃 | 风险级别、原始记录、权限与状态不变 |

模型不得写入 `goal.health`、执行状态、审批结果、组织配置和审计原记录。
规则风险是最低关注层级：`at_risk` 不能因建议 `on_track` 变绿；待审批和关键失败不能被低关注建议降序到不可见。
`needsAttention=false` 不能删除、折叠或过滤原始失败行；排序仅在相同规则风险层内使用建议，保持原始列表可达。
建议的“已采用”与事项的“已解决”独立；前者不能触发后者。

## 10. 可复现验收矩阵

以下为待执行用例，当前执行结果全部为 `NOT RUN`。使用固定 fixture、固定时钟和可控 Jev stub，先验证行为边界。

| ID | 输入／操作 | 必须观察到的结果与证据 |
| --- | --- | --- |
| AC-01 | 禁用或缺少 key，读取 Goals / Reports | 无出站请求；原有契约、健康控件、原始行数与基线一致 |
| AC-02 | `at_risk` + 模型 `on_track` | 规则仍为警示色与风险文案；建议未采纳；原始健康字段不变 |
| AC-03 | 关键失败／待审批 + `needsAttention=false` | 行仍存在且保持规则风险优先层；不能隐去或推到不可见 |
| AC-04 | 模型 `blocked`，有／无对应审批或会话 | 只为真实且可访问对象展示入口；无对象时不造假链接 |
| AC-05 | 点击查看、应用建议、准备交接 | 网络记录中无 turn POST、重试、审批决策或目标／组织 PATCH |
| AC-06 | 同成员、无任务意图；或缺验收材料 | 明确弃权；不推荐接力／并行，不输出整体通过 |
| AC-07 | 超时、429、坏 JSON、越界选项、低置信 | 有界退化；原页面可操作；不把错误或弃权写成成功建议 |
| AC-08 | 取得建议后改摘要、删除岗位或切换工作区 | 旧建议失效；无跨工作区引用与错误派工 |
| AC-09 | 关闭 opt-in，输入框含唯一测试标记 | 抓取请求、日志、导出均不出现该标记；未请求的正文不出站 |
| AC-10 | opt-in 仅选一个摘要／片段，另有未选材料 | 请求仅含确认过的白名单字段；未选材料与密钥均不泄露 |
| AC-11 | 伪造／失效证据引用、材料版本冲突 | 对应项无法判断；不能把断链材料显示为已覆盖证据 |
| AC-12 | 一项动作成功、其他动作失败或验收待完成 | 分别显示回执；不自动标记整个事项解决 |
| AC-13 | 模型建议出现前后比较存储与审计快照 | 模型不改原始字段；只允许用户明确动作产生原有业务写入 |
| AC-14 | 同一输入重复加载、接口迟到和服务不可用 | 调用次数受限；迟到结果不覆盖更新状态；关闭开关可回退 |

实现验收保留请求记录、关键界面、存储差异与 fixture 版本；stub 用例通过不能证明真实模型质量。
真实服务验证另记模型／问题版本、调用结果与成本；产品验收须实际走完查看、处理及回执，不以 CI 代替。

## 11. 50 条真实历史样本试点
